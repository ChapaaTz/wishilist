Events Ticket Module.

A focused extension to the existing Chapaa campaign link that turns a fundraising page into a fixed-price ticket sale — starting with the Jerusalem Children's Home Marathon 2026. Each purchase issues unique, verifiable ticket codes delivered by self-sufficient WhatsApp & SMS, with a public ticket page and an owner dashboard for attendee management.

01

What changes

A ticket campaign reuses the existing public campaign link structure but behaves differently from a donation campaign. The page no longer asks "how much?" — the price is fixed and the user chooses how many tickets.

Crowdfunding page (today)

  • Open "amount raised" + % funded + goal bar
  • Variable contribution amount entered by donor
  • Contribute button
  • Pledge button
  • Open App button
  • No record issued back to the contributor

Ticket page (new)

  • One or more ticket tiers, each at its own fixed price tiers
  • Per-tier quantity steppers instead of a free amount
  • Live order summary = Σ (tier price × qty)
  • Pay with Mobile Money button new
  • Pay with Card · Selcom button new
  • Issues one unique code per ticket purchased new
💡

Reuse, don't rebuild. The campaign type field gains a value ticket. The renderer branches on type: donation keeps the current UI; ticket shows the fixed-price purchase flow described here. The shared link format (/c/{slug}) is unchanged.

02

The ticket page

Same visual language as the current campaign card. The progress/goal block is replaced by a list of ticket tiers — an event can offer several (5KM, 10KM, 21KM…) each at its own fixed price. The buyer sets a quantity per tier, sees a live order summary, and pays with one of the two methods.

Payment branch detail

📱 Mobile Money
  • User enters MSISDN (or it's prefilled from account)
  • USSD push / STK prompt to the phone
  • User approves with mobile-money PIN on device
  • Gateway webhook confirms → transaction marked paid
  • Supports M-Pesa, Mixx by Yas (formerly Tigo Pesa), Airtel Money, Halopesa
💳 Card Payment · via Selcom
  • Card payments run on Selcom infrastructure
  • Selcom hosted card form (PCI-scope stays with Selcom)
  • 3-D Secure challenge where required
  • Authorise → capture, then Selcom webhook → paid
  • Visa / Mastercard
🔐

Ticket codes are generated only after the payment webhook confirms a settled transaction — never on the client. This prevents issuing valid tickets for failed or pending payments.

05

Data model

Two new tables: ticket_tiers defines the priced options an event offers (5KM, 10KM…), and tickets holds each issued ticket, linked to a tier, a buyer and the transaction that paid for it. Every ticket carries its own unique, shareable code.

Relationships

// An event (campaign) offers several priced tiers Campaign 1 ──< TicketTier // 5KM @25k, 10KM @30k, 21KM @50k … // One purchase → one transaction → many tickets, each of a chosen tier User 1 ──< Transaction 1 ──< Ticket TicketTier 1 ──< Ticket // ticket inherits its tier's price & name Campaign 1 ──< Ticket // denormalised for fast owner queries

ticket_tiers new table

CREATE TABLE ticket_tiers ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), campaign_id UUID NOT NULL REFERENCES campaigns(id), name VARCHAR NOT NULL, // "5KM Fun Run" price BIGINT NOT NULL, // fixed price, in cents (25000_00) currency CHAR(3) DEFAULT 'TZS', capacity INT, // null = unlimited; else stock cap sold_count INT DEFAULT 0, // for "X left" + sold-out logic max_per_order INT DEFAULT 10, // per-tier purchase limit sort_order INT DEFAULT 0, is_active BOOLEAN DEFAULT true );

tickets new table

CREATE TABLE tickets ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), ticket_code VARCHAR(12) NOT NULL UNIQUE, // e.g. 7K9-QX2 (human-readable) tier_id UUID NOT NULL REFERENCES ticket_tiers(id), transaction_id UUID NOT NULL REFERENCES transactions(id), user_id UUID NOT NULL REFERENCES users(id), campaign_id UUID NOT NULL REFERENCES campaigns(id), price_paid BIGINT NOT NULL, // snapshot of tier price at purchase holder_name VARCHAR, // optional per-ticket name public_token VARCHAR(32) NOT NULL UNIQUE, // for the public view URL status VARCHAR DEFAULT 'valid', // valid | used | void checked_in_at TIMESTAMPTZ, // set when scanned at gate created_at TIMESTAMPTZ DEFAULT now() );

Field reference

FieldPurposeNotes
tier_idWhich priced option this ticket belongs toDrives the name & price shown on the ticket
price_paidPrice snapshot at purchase timeStays correct even if the tier price changes later
ticket_codeShort code printed on the ticket & shown to staff at the gateUnique, uppercase, no ambiguous chars (no O/0, I/1)
public_tokenRandom opaque token used in the public link, not the codeKeeps the gate code from leaking in URLs
statusLifecycle of a single ticketvalid → used → void
checked_in_atSingle-use enforcement at the event gateRe-scan of a used ticket is flagged

Code generation rules

  • For each tier in the order, generate one ticket per unit, all inside a single DB transaction (atomic — all or nothing).
  • ticket_code: 7 chars from a 32-symbol alphabet (Crockford base32, excludes I/L/O/U) grouped XXX-XXX for readability.
  • Collision check on insert; retry on the rare unique-constraint violation.
  • public_token: 22+ chars of cryptographically random URL-safe text.

Public ticket link

// Self-sufficient — no login needed to view a single ticket https://chapaa.app/t/{public_token} // Shows: event name, date, holder, ticket_code, QR, status, "add to wallet"
06

Delivery: WhatsApp & SMS

Both messages are self-sufficient — a recipient can act on either one without the other. WhatsApp carries the rich ticket cards, QR and a "view all" button; SMS carries the code(s) plus a short public link as a fallback for any phone.

08

Suggested build order

Phase 1 — Sell & issue

  • Add ticket campaign type + ticket_tiers table
  • Organiser create-tickets form (name, date, tiers)
  • Per-tier quantity steppers, order summary, two payment buttons
  • tickets table + atomic code generation on webhook
  • WhatsApp + SMS delivery with public link

Phase 2 — Manage & verify

  • Owner dashboard: list, search, stats, export
  • Public ticket page /t/{token} + wallet passes
  • Gate scan mode + single-use enforcement
  • Refund / void handling
